# 03. 수집·파싱 실패 처리 규칙 (관문 A)

작성일 2026-09-14. 00b 검토 메모(A5, A6) 반영(09-14 밤). 「상품 못 찾음」 판정(문자열 유사도 임계치 포함)은 05(data-scientist)의 몫이므로 여기서는 다루지 않고 참조만 한다. 재시도 횟수·간격 등 구체적 수치는 실제 실패율 데이터가 없어 전부 잠정값이다.

## 수집 실패

**판정 기준** (잠정값 포함)

| 기준 | 조건 |
|---|---|
| HTTP 오류 | 4xx / 5xx 응답 |
| 빈 응답 | 응답 바디 0바이트, 또는 필수 필드 누락 |
| 스키마 불일치 | 소스가 정의한 응답 스키마와 실제 응답 구조가 다름 |
| 본문 형식 불일치 | DART `download.do` 응답이 HTTP 200이어도 Content-Type이 `application/pdf`가 아니면 실패 |
| **빈 결과 (12 반영, 신설)** | 조회 조건이 맞는데 0행이 오면 **실패로 본다**. 금투협은 `uRptAllYN`을 빠뜨리면 HTTP 200 + 정상 XML + 0행을 돌려준다. 위 판정 기준 어디에도 걸리지 않으므로 별도 행이 필요하다 |
| **응답 절단 (12 반영, 신설)** | 종료 태그(`</root>`)로 끝나지 않으면 실패. 그리고 응답이 주는 총건수(`dbio_total_count_`)와 실제 파싱된 행 수가 다르면 실패 |

**소스별 보완(web-verify 반영, 08 참조)**
- DART 펀드공시 수집 필터는 `pblntf_detail_ty` G001·G002·G003 코드로 걸고, 문서 종류(투자설명서 / 간이투자설명서 / 일괄신고서 / 효력발생안내)는 보고서명 문자열로 판별한다. 둘을 섞으면 누락이 생긴다(A2).
- DART 투자설명서는 `document.xml`(표지) 한 번, `download.do`(본문 PDF) 한 번, 접수번호당 요청이 둘이다. 둘 중 하나만 실패해도 원본파일 표(01)에는 두 행이 각각 남는다(A1).
- 제재공시는 게시판 크롤링이 아니라 금감원 검사결과제재 OPEN API로 받는다. 인증키 신청이 선행된다(D4).
- **금투협은 요청이 셋이다 (12 반영)**: 목록(`DISFundFTimeAnnSO.selectAnn`) → 행별 첨부 목록(`DISFtimeDetSO.select`) → 파일 다운로드. **다운로드는 `disdown.kofia.or.kr`로 호스트가 다르다.** 세 단계가 각각 실패할 수 있으므로 원본파일 표(01)에 단계별로 행이 남는다.
- **KRX는 발급과 이용 승인이 별개다 (13 반영)**: 키가 있어도 서비스별 승인이 없으면 호출이 막힌다. 응답 메시지로 구분한다 — `Unauthorized API Call`은 **승인 대기**, `Unauthorized Key`는 **키 문제**다. 이 둘을 섞으면 승인 대기 중인 키를 계속 재발급하며 시간을 태운다.
- **KRX 우회로는 없다 (13 반영)**: `data.krx.co.kr`의 `getJsonData.cmd`는 세션을 요구해 `LOGOUT`만 돌려준다. 공식 Open API가 유일한 경로다.
- **KRX `ISU_NM`은 상장 약명이지 펀드명이 아니다 (13 반영)**: `1Q 200액티브` 대 `하나1Q200액티브증권상장지수투자신탁[주식]`. 이름 완전일치로 조인을 설계하면 매칭률이 0.0%다.
- **금투협 응답은 `curl`로 받는다 (12 반영)**: Python `urllib`로 받으면 1,499행 중 43행만 도착한다. 잘린 XML은 파서가 행을 **조용히 적게** 세고 원본은 저장되며 수집은 성공으로 기록되므로, 사후 발견이 거의 불가능하다. 위 「응답 절단」 판정이 이것을 잡는다.

**격리 위치**

**결정**: 실패한 수집도 파일은 정상 경로(02의 `raw/{source}/{collected_date}/{source_doc_key}__v{n}.{ext}`)에 그대로 저장하고, 별도 격리 폴더로 옮기지 않는다. 대신 원본파일 표(01)의 `collect_status` 칼럼(`success` / `failed` / `permanent_failed`)으로만 격리를 표현한다.
**근거**: 02의 원본 불변 원칙을 수집 실패 응답에도 동일하게 적용하는 편이 규칙을 하나로 유지할 수 있어 단순하다. 파일 이동은 별도 표를 하나 더 늘리는 것과 같은 효과이므로, 표 하나가 없으면 무엇이 안 되는지 답할 수 없다면 만들지 않는다.

**재시도 정책 (00b 반영, A5)**

**결정**: 타임아웃과 5xx만 지수 백오프 5회 재시도한다. 4xx 중 403은 설정 오류이므로 재시도 없이 즉시 알림한다. 그 외 4xx는 `permanent_failed`로 바로 처리한다.
**근거**: 기존 3회·1시간→6시간→24시간 규칙은 실패율 데이터 없이 잡은 잠정값이었다. 403은 인증키·권한 등 설정 문제일 가능성이 높아 재시도로 해결되지 않으므로 사람이 바로 개입하는 편이 낫고, 그 외 4xx(요청 자체가 잘못됨)도 재시도로 해결되지 않으므로 영구 실패로 바로 넘긴다. 타임아웃·5xx만 일시적 실패일 가능성이 있어 재시도 대상으로 남긴다.

**영구 실패 처리**

**결정**: 재시도를 모두 소진하거나(타임아웃/5xx 5회) 재시도 대상이 아닌 4xx(403 제외)를 만나면 원본파일(01).collect_status를 `permanent_failed`로 고정하고 더 이상 자동 재시도하지 않는다.
**근거**: 무한 재시도는 실패 원인이 소스 측 영구 변경(URL 폐기 등)일 때 자원만 소모한다. 사람이 개입해 재시도 정책을 리셋하는 경로는 관문 B(Airflow 등 오케스트레이션 구축) 사안이다.

## 금투협 클래스 행 중복 제거 (00b 반영)

**결정 (12 반영)**: 수집 단계에서 `uRptGb = 'O'`(수시공시)인 행만 대상으로, 01의 자연키 `(companyCd, standardDt, announceTtl, tmpV1)`가 같은 묶음을 문서 1건으로 접는다. PDF는 sha256으로 1회만 받는다.
**근거**: 금투협 수시공시는 클래스 행 단위로 여러 행이 조회된다(모 1 + 클래스 N). 행 단위로 그대로 수집하면 같은 공고를 여러 번 내려받고 여러 번 추출하게 된다. 02의 「같은 해시면 다시 내려받지 않고 추출도 하지 않는다」 규칙과 함께 적용한다.
**접는 키에서 `tmpV1`을 빼면 안 된다 (12 3절)**: 제목과 날짜만으로 접으면 운용사가 같은 날 같은 제목으로 공시한 서로 다른 펀드가 한 묶음이 된다. 표본에서 삼성자산운용 2026-08-13 「투자설명서 변경」이 펀드 72종 234행으로 뭉쳤다.
**확인됨(12)**: 15행은 클래스 행이 맞다(모 1 + 클래스 14). 다만 중복 제거는 **수시공시에만** 걸어야 한다. 조건에 `uRptGb = 'O'`(tsCd `2OF…`)를 반드시 붙인다. 정기공시(`2RF…`)는 클래스·펀드마다 별도 보고서라 평균 묶음 크기가 1.08이고, 여기에 중복 제거를 걸면 서로 다른 보고서를 하나로 지운다.
**확정(12 6절)**: 15행은 동일 파일 집합을 가리킨다(운용사 4곳 묶음 4개 검증). 중복 판정은 `DISFtimeDetSO`가 주는 `fileNm`(서버 저장명) 비교로 다운로드 **전에** 끝내고, sha256은 받은 뒤 기록만 한다.

## 본문 추출 실패

**판정 기준** (잠정값)

| 기준 | 조건 |
|---|---|
| 텍스트 길이 하한 | 추출된 section_text가 500자 미만 |
| 깨진 문자 비율 | 한글·영숫자·기본 문장부호 이외 문자가 30%를 초과 |
| 형식 미지원 | HWP 3.0(자체 바이너리, 5.0 파서 불가), 배포용 HWP(암호화), 텍스트 레이어 없는 PDF(스캔). 문서.body_format으로 판별. HWP 5.0의 PrvText 스트림은 앞부분만 복구되므로 성공으로 치지 않는다(web-verify G1~G3) |

**본문 추출 실패 상태값 (00b 반영, A5)**

이 값들은 01 원본파일(raw_object) 표의 `extract_status` 칼럼에 들어간다.

| 상태값 | 조건 | 자동 재시도 |
|---|---|---|
| EXTRACT_UNSUPPORTED_FORMAT | HWP 3.0. 분쟁조정 첨부 94건 실측 | **제외** |
| EXTRACT_PARTIAL | 배포용 HWP, 7건. PrvText로 약 1,022자 부분 복구 | **제외** |
| OCR_CANDIDATE | BMP 내장 4건. 보조 플래그 | 대상 |
| EXTRACT_NOT_APPLICABLE | DART `document.xml`처럼 본문이 원래 없는 파일 | 해당 없음(실패 아님) |

**근거**: HWP 3.0과 배포용 HWP는 해결되지 않는 실패다. 매일 반복해서 재시도하면 리소스만 쓰고, 진짜 일시적 실패(네트워크 오류 등)를 찾는 신호도 묻힌다(00b A5).

**플래그 위치**

**결정**: 문서 단위 실패는 문서 표(01)의 `parse_status`(하위 원본파일 extract_status의 집계값)에, 파일 단위 실패는 원본파일 표(01)의 `extract_status`에, 절 단위 실패는 절 표(01)의 `extract_status`에 각각 남긴다.
**근거**: 파싱은 문서를 텍스트로 바꾸는 단계 전체의 성패이고, 본문 추출 실패는 그 중 특정 파일·절이 깨졌는지를 가리는 더 세밀한 판정이라 층위가 다르다. 플래그를 하나로 합치면 「문서는 파싱됐는데 특정 첨부·절만 깨진」 경우를 표현할 수 없다.

**격리와 재처리**

**결정**: 추출 실패한 절은 section_text를 원문 그대로(정규화 이전 상태) 두고 extract_status만 `failed`로 표시한다. 실패한 절만 다시 처리하는 큐·스케줄은 만들지 않는다.
**근거**: 재처리 오케스트레이션은 관문 B 사안이다. 09-16 시점에는 「실패를 어디서 알아볼 수 있는가」만 정하면 09-17 수집 개발이 시작할 수 있다.
