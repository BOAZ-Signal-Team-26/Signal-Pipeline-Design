## 1. DART 펀드코드 대조 — 7/10

`gate-a/09`에서 DART 투자설명서 표지 10건으로 확보한 펀드코드를 포털 `srtnCd`에서 찾았다.

| 결과 | 코드 |
|---|---|
| 존재 | E4675, B2170, E5771, E0136, CY091, AT146, AO119 |
| 없음 | EY758, EZ258, EZ029 |

**판정**: 두 값은 **같은 체계가 맞다.** 찾아진 7건 모두 펀드명·표준코드가 정합했다(예: `E4675` → 신한미국나스닥100인덱스증권자투자신탁, `K55210E46751`).

**없는 3건은 오류가 아니다.** DART는 설정 이전부터 공시가 올라오고 포털 코드 등록은 그보다 늦다(팀 09-05 기록: 설정일 대비 6일 지연 2건). 즉 **`01`의 `PENDING_MASTER`가 가정한 바로 그 상태**다. 매칭 실패로 세지 말고 정상 대기로 처리한다.

## 2. `srtnCd`는 전역 유일이 아니다 (새 발견)

**`srtnCd` = `asoStdCd[6:11]`이 100% 일치한다**(표본 5,000건 전수). 즉 독립 코드가 아니라 **협회표준코드 12자리 안의 한 토막**이고, 앞 6자리(체계 + 운용사)가 다르면 같은 토막이 나올 수 있다.

| 항목 | 값 |
|---|---|
| 고유 `srtnCd` | 165,118종 |
| **2건 이상이 공유하는 코드** | **4,899종 (3.0%)** |
| 그중 `asoStdCd`도 다른 것 | 4,899종 **전부** (= 진짜 다른 펀드) |
| `basDt`만 다른 스냅숏 중복 | 132종 |

예: `20061`이 `KR5104200617`(개인연금 혼합 투자신탁 2호, 1994), `KR5106200615`(한남안정주식투자신탁 3호, 1994), `KR5204200616`(해피드림주식투자신탁20C-1호, 1997) 셋에 걸쳐 있다.

**그래도 우리 범위에서는 안전하다.**

| 범위 | 겹침 |
|---|---|
| 2015년 이후 설정 펀드끼리 | **5종** (10행) |
| 「상장지수」 1,435건 안 | **0종** |
| `(asoStdCd 앞 6자리, srtnCd)` 쌍 | 183,648종 중 **1종** |

**결정**: `short_code` 단독 조인을 유지한다.
**근거**: 겹치는 4,899종은 대부분 1990년대 구펀드이고, CDI 대상인 공모 펀드·ETF에서는 사실상 겹치지 않는다. 지금 복합키로 바꾸면 얻는 것 없이 조인이 복잡해진다.
**단서**: 겹침이 실제로 문제가 되면 `(asoStdCd 앞 6자리, srtnCd)` 쌍으로 올린다. `asoStdCd`는 이미 상품 표의 `standard_code`에 있으므로 **스키마 변경 없이** 가능하다.
**미확인**: 구펀드가 실제 수집 대상에 들어오는지. 「공모로 한정하되 필터는 적재 단계」(`00b` A8) 규칙에 따라 원본은 전량 보관하므로, 적재 필터가 구펀드를 거르는지 확인이 필요하다.

## 4. J8 — 판매회사 명단 소스를 찾았다

`01` 미확인 16(「판매회사 명단의 소스」)이 열려 있었다. 후보는 (a) 투자설명서 PDF 본문, (b) 금투협 전자공시 둘이었다.

**답: (b) 금투협 전자공시다. 그리고 문자열이 아니라 코드로 붙는다.**

### 서비스 둘

```
판매회사 마스터
POST /proframeWeb/XMLSERVICES/   FS-DIS2^DISMngCompInqSO^select
<DISMngCompInqListDTO><option>S2</option><standardDt>202608</standardDt></DISMngCompInqListDTO>
→ saleCompCd + koreanNm, 200건

판매사별 펀드 목록 (상품_판매사 브릿지)
POST /proframeWeb/XMLSERVICES/   FS-DIS2^DISSalesCompFeeCmsSO^select
<DISCondFuncDTO><tmpV11>{판매사코드}</tmpV11><tmpV30>{기준일 YYYYMMDD}</tmpV30>
  <tmpV12/><tmpV3/><tmpV5/><tmpV4/></DISCondFuncDTO>
→ 행 요소는 <selectMeta>. tmpV17 = 표준코드, tmpV18 = 운용사코드, tmpV2 = 펀드명
```

**주의**: 행 요소가 `<list>`가 아니라 **`<selectMeta>`**다. 금투협의 다른 서비스와 다르다.

### 실측

| 판매사 | 행 수 | 고유 표준코드 | 「상장지수」 |
|---|---|---|---|
| 신한은행 (A02015) | 3,093 | 3,093 | **0** |
| 국민은행 (A02008) | 3,955 | 3,955 | **0** |

두 판매사의 표준코드 교집합은 1,397건, 신한 전용 1,696건, 국민 전용 2,558건이다. **판매사마다 목록이 실제로 다르다** — 브릿지 데이터가 맞다.

**결정**: `상품_판매사` 표는 이 서비스로 채운다. 판매사 200곳을 순회하며 `(tmpV17 표준코드, 판매사코드)` 쌍을 적재한다.
**근거**: 위 표. 표준코드가 판매사 안에서 유일하고(3,093행 = 3,093종), 판매사별로 목록이 다르다.
**규모**: 판매사 200곳 × 평균 3,000건 ≈ **60만 행**. 월 스냅숏이므로 기준일을 함께 적재한다.

### J8의 판정이 바뀐다 — 문자열이 아니라 코드

`01` 조인 대조표 J8은 「판매사명은 **문자열 매칭**(05 9절, 임계치 0.95)」으로 적혀 있었다. **바꾼다.**

**결정**: J8은 **코드 매칭**이다. `saleCompCd`와 표준코드가 둘 다 있으므로 법인명 문자열 매칭이 필요 없다.
**근거**: 금투협이 판매사 코드를 직접 준다. 이름으로 맞출 이유가 없다.
**함의**: `05` 9절(법인명 정규화)의 적용 대상이 **J12 제재공시 하나로 줄어든다**. 9절을 없애지는 않는다 — 제재공시는 금융회사명 문자열만 주므로 여전히 필요하다.

### 한계 — ETF는 이 소스로 판매사를 붙일 수 없다

두 판매사 모두 「상장지수」가 **0건**이었다. ETF는 거래소에서 사는 상품이라 판매사 개념이 다르다.

**미확인**: ETF의 판매사 축을 어떻게 볼 것인가. 애초에 필요한지부터 정해야 한다 — 분쟁조정을 판매사 축에 붙이는 것이 `상품_판매사`의 목적인데(`01`), 분쟁조정 187건에 ETF 사건이 있는지는 확인되지 않았다. 없으면 이 한계는 문제가 아니다.

## 5. J14 — 분쟁조정에는 판매사명도 없다

`01` 미확인 4(「분쟁조정 결정문 텍스트에 판매사명이 식별 가능한 형태로 남아 있는지」)가 열려 있었다. 게시판에서 결정문 8건을 받아 본문을 추출했다.

### 방법

FSS 게시판(`B0000390`)은 본문이 비어 있고 HWP 첨부만 준다. HWP 5.0은 OLE 복합문서라 `BodyText/Section0`을 zlib(raw deflate)로 풀고 `HWPTAG_PARA_TEXT`(태그 67) 레코드에서 UTF-16LE 텍스트를 꺼낸다. 파서는 `scripts/hwp_text.py`(외부 의존성 없음).

### 결과 — 8건 전부 마스킹

| nttId | 추출 글자수 | 피신청인 표기 |
|---|---|---|
| 229094 | 19,767 | `●●손해보험㈜` |
| 229093 | 15,584 | `●● 보험㈜` |
| 219340 | 20,514 | `●●증권` |
| 218695 | 10,906 | `●●손해보험㈜` |
| 217927 | 15,358 | `●●카드㈜` |
| 217926 | 11,044 | `●●●●증권` |
| 217925 | 21,298 | `●●은행` |
| 136595 | 12,540 | `○○○○○○ 주식회사` |

**결정**: 분쟁조정 결정문은 `문서.distributor_id`를 채울 수 없다. `01`이 예고한 「미연결 레코드」 시나리오가 확정됐다.
**근거**: 위 표. 8건 전부 회사명이 `●`·`○`로 가려졌다. 펀드명도 `▣▣ ▤▤▤▤▤ 아시아 무역금융 전문투자형 사모투자신탁1호`처럼 고유명만 가려진다.

**다만 업종은 남는다.** 증권 / 은행 / 보험 / 카드 / 손해보험이 구분된다. 상품이나 개별 판매사로는 못 붙여도 **판매 채널 유형 축으로는 쓸 수 있다.** 채택 여부는 관문 C(검증 설계) 사안이다.

**표본 한계**: 8건은 게시판 최신순이라 최근 문서에 쏠려 있고, 그래서 추출률이 8/8이다. 팀의 09-05 기록(213단위 중 112건, 52.6%)과 다른 이유는 실패분 94건이 1999~2004년 HWP 3.0이기 때문이다. 이 파서도 HWP 3.0은 못 읽는다. **마스킹 패턴이 과거 문서에서도 같은지는 미확인**이지만, 개인정보 보호 목적이라 완화됐을 가능성은 낮다.

### 05에 미치는 영향

`05` 6절은 「코드가 영원히 없는 소스(**분쟁조정**·제재공시)」의 자동 확정 규칙을 판매사명 유사도 0.95로 정했다. **분쟁조정에는 적용할 대상이 없다** — 판매사명 자체가 마스킹이다. 6절은 제재공시에만 유효하다.

`05` 7절의 라벨 200건 표본도 「분쟁·제재 187건 전건 수동 확인」을 전제로 하는데, 분쟁조정 187건은 **수동으로도 붙일 수 없다.** 표본 설계를 다시 잡아야 한다. **관문 C 사안**으로 넘긴다 — 라벨은 임계치 확정용이고 임계치는 관문 A의 잠정값으로 충분하다.

### 검증 라벨(골든셋)에 대한 경고

`00`은 CDI 검증 방법을 「분쟁조정결정례에 등장한 상품군의 CDI가 그렇지 않은 상품군보다 유의하게 높은지」로 정의했다. 상품도 판매사도 못 붙이면 이 검증이 성립하지 않는다.

**미확인**: 본문에 남는 상품 **유형**(「전문투자형 사모투자신탁」 등)만으로 상품군 수준의 대조가 가능한지. 다만 조사 상세가 이미 지적했듯 분쟁조정은 대부분 **사모펀드 투자제안서**이고 우리 측정 대상은 공모 투자설명서라, 이 불일치가 더 근본적이다. **관문 C에서 검증 설계를 다시 봐야 한다.**

## 6. J12 — 제재공시는 판매사에 붙고 상품에는 영원히 안 붙는다

키 없이 판정했다. 금감원이 **응답 샘플과 결과변수 표를 스펙 페이지에 공개**하기 때문이다
(`OPEN API > 상세 및 테스트 > 검사결과제재 API`). 인증키는 호출에만 필요하고, 형태 판정에는 필요 없다.

### 인터페이스

```
GET https://www.fss.or.kr/fss/kr/openApi/api/openInfo.jsp
    ?apiType={xml|json}&startDate=YYYY-MM-DD&endDate=YYYY-MM-DD&authKey={32자리}
```

요청 변수는 **넷뿐이다** — 응답방식·시작일·종료일·인증키. 금융회사도, 업종도, 페이지도 없다.

공식 샘플의 `actObjContent`를 그대로 옮긴다.

> 잘못 매수한 **㉮펀드**(가입액 10백만원)를 환매하고 … **乙** 본인 자금으로 ㉮펀드를 매수하여 **甲**에게 …
> **A지점**은 2007.11.1. … **B지점** 등 9개 지점에서는 … **㈜C**(대표 戊) 등 15개 업체에 대하여

상품은 `㉮펀드`, 사람은 `甲·乙·丙·丁·戊`, 지점은 `A지점`, 거래처는 `㈜C`다.
`5`절의 분쟁조정과 **같은 마스킹 체계**다. 차이는 하나뿐이다.

| | 판매사명 | 상품명 |
|---|---|---|
| 분쟁조정 (J14) | 마스킹 `●●증권` | 마스킹 |
| **제재공시 (J12)** | **실명 `finInstName`** | **마스킹** |

**결정**: J12는 **확인됨**. `finInstName` ↔ 판매사 표로 붙는다.
**동시에**: 제재공시 문서는 **문서_상품 브릿지 행을 만들지 않는다** (문서 표의 단일 `product_id` FK는 `01`에서 이미 브릿지로 바뀌었다). `01`의 `NO_CODE_IN_SOURCE`가 맞는 판정이었고, 그 이유가 「코드가 없다」가 아니라 **「상품이 가려져 있다」**임이 확정됐다.

**함의**: 제재는 상품 단위 신호가 아니라 **판매사 단위 신호**다. CDI를 상품에 붙이는 축과 제재를 판매사에 붙이는 축은 층이 다르다. 검증 설계에서 이 둘을 같은 축으로 놓으면 안 된다(관문 C).

### 표기 — 정규화가 먹지만 외은지점이 걸린다

샘플 값은 `교통은행`이다. 법인격 표기(`주식회사`·`㈜`)가 **없는 약칭**이라 `05` 9절의
1~4단계(NFKC → 구 상호 치환 → 법인격 제거 → 공백 제거)는 사실상 할 일이 없고, 5단계(지점 표기 제거)만 남는다.

**단 `교통은행`은 외국은행 국내지점이다.** 금투협 판매회사 마스터 200곳(`4`절)에는 펀드를 파는 회사만 있으므로, 제재 대상 금융회사 중 상당수(외은지점·저축은행·카드·보험)는 **판매사 표에 아예 없다**. 이것은 매칭 실패가 아니라 정상이며, `NO_CANDIDATE`가 아니라 **대상 외**로 분류해야 한다. 미분류로 두면 실패율이 부풀려진다.

### 05 6절을 좁혀야 한다

6절의 자동 확정 조건은 「0.95 이상 **AND** 단독 후보 **AND** 교차 확인(제재조치일·**문서 내 다른 식별 정보** 일치)」다.
**「문서 내 다른 식별 정보」에 해당하는 것이 없다.** 상품도 지점도 거래처도 전부 가려져 있다.
교차 확인에 쓸 수 있는 것은 `actReqDate` 하나뿐이고, 같은 날 여러 회사가 제재받는 일은 흔하므로 변별력이 약하다.

→ 6절의 조건을 **「0.95 + 단독 후보 + `actReqDate` 일치」**로 실측에 맞게 고쳐 쓴다. 표현만 정확해지는 것이고 기준은 그대로다.

### 수집 설계에 걸리는 것 넷

| 사항 | 내용 |
|---|---|
| **워터마크를 `emOpenSeq`로 잡을 수 없다** | `03` 표가 「`emOpenSeq` 최대값」으로 적어 뒀으나, `emOpenSeq`는 **검사 내 순번**이고 애초에 **요청 변수에 없다.** 증분 조회는 날짜로만 가능하다 |
| 필터 대상 필드 불명 | `startDate`/`endDate`가 `actReqDate`에 걸리는지 `inputDate`에 걸리는지 스펙에 없다. 샘플은 조치일 04-24, 입력일 04-27로 **사흘 차이**다. 정정·지연 입력을 놓치지 않으려면 룩백이 필요하고, 룩백 폭은 이 확인 뒤에 정한다 → **키 받으면 1분** |
| 페이징 없음 | 요청 변수에 페이지가 없다. 5,700여 건 전량 백필은 **기간 분할**로만 가능하다 |
| 날짜 형식 3종 | 요청 `YYYY-MM-DD` / `actReqDate` `2026.04.24` / `inputDate` `2026-04-27 10:14:12`. 파서에서 통일 |

**JSON 루트 키는 `reponse`다.** `response`가 아니다. 금감원 스펙의 공식 샘플이 그렇게 적혀 있으므로 파서는 오타를 그대로 따라야 한다. `response`로 짜면 전건 0으로 조용히 실패한다.

**인증키**: 32자리. 법인 신청은 **요청 IP 등록**이 따른다(`인증키 신청 > 요청 IP 변경 신청(법인용)` 메뉴가 별도로 있다). 수집 서버 IP가 정해지기 전에 법인 키를 신청하면 재신청이 필요하다.

### 경영유의사항 등 공시 API는 같은 표의 두 번째 뷰다 (09-20 추가)

금감원 OPEN API 목록에는 **「금융회사 경영유의사항 등 공시 API」**가 따로 있다
(`.../openApi/api/openInfoImpr.jsp`). 두 스펙 페이지의 공개 샘플을 필드 단위로 대조했다.

| | 검사결과제재 | 경영유의사항 등 |
|---|---|---|
| 요청 변수 | `apiType`·`startDate`·`endDate`·`authKey` | **동일** |
| 결과 필드 | 13개 | **이름까지 동일** |
| `examMgmtNo` (검사관리번호) | `202500751` | **`202500751` — 같다** |
| `emOpenNo` (제재정보번호) | `2025007511` | `2025007512` |
| `emOpenSeq` | `1` | `2` |
| `transCode` | `0` | `1` |
| `actGbn` | `10` | `20` |
| 나머지 8개 필드 | | 값까지 동일 |

**한 검사(`202500751`)에서 나온 조치 둘이 순번 1·2로 갈린 것이다.** 이것이
6절의 판정 — 「`emOpenSeq`는 전역 증가 번호가 아니라 검사 내 순번」 — 을 확증한다.

**설계에 주는 답 셋**

1. **파이프라인을 새로 만들 필요가 없다.** 파서·자연키·적재 경로가 같고 URL만 다르다.
   `--kind` 한 옵션으로 끝난다(`scripts/fetch_fss_sanctions.py`).
2. **`document_type`만 나누면 된다.** `transCode`/`actGbn`이 구분자다.
   `01`의 문서 표에 `제재공시` 외에 **`경영유의공시`**를 추가한다.
3. **`emOpenNo`는 두 소스가 같은 번호 공간을 쓴다**(…7511 / …7512). 합쳐도 자연키가
   충돌하지 않을 가능성이 높으나 **실측 전까지는 `(kind, emOpenNo)`를 키로 둔다.**

**미확인 — 본문의 마스킹 수준.** 두 샘플의 `actObjContent`가 **글자 하나까지 같다.**
금감원이 같은 예시 텍스트를 양쪽에 붙여 넣은 것이므로, 경영유의사항 본문이 제재와
같은 마스킹(`㉮펀드`·`甲`·`A지점`)인지는 **이 샘플로 판정할 수 없다.** 필드 구조만
확실하다. 키를 받으면 실제 본문 몇 건으로 확인한다.

**채택 여부는 여기서 정하지 않는다.** 경영유의사항은 팀이 정한 소스 6종에 없다.
다만 `5`절에서 분쟁조정이 골든셋으로 쓸 수 없게 확정된 뒤라, **판매사 단위 라벨**의
후보로는 값이 있다(제재보다 가벼운 조치라 건수가 많을 것으로 보인다). 제재와 마찬가지로
상품에는 붙지 않으므로 검증은 「CDI 높은 **상품**이 분쟁이 많다」가 아니라
「CDI 평균이 높은 **판매사**가 조치를 많이 받는다」 형태의 약한 대조가 된다.
**09-20 미팅 안건으로 올린다.**
