# 16. 소스별 데이터 현황표 (7항목 × 문서 4종)


> 09-22 정합성 보완: 현재 스키마·키·실행/모집단 계약은 [논리 스키마](01_logical_schema.md)와 [검토 보고서](18_schema_review.md)를 우선한다.

「데이터 가져온거 보고 분석해보기」 티켓(정담당 주영 / 부담당 대현, 마감 09-14)의 산출물이다.
09-20에 대현이 작성했다. **완료 체크는 하지 않았다** — 조건 3(샘플 머지)·4(싱크 공유)는 주영 몫이다.

`15`가 「어떻게 받아오나」라면 이 문서는 **「받아보니 무엇이 들어 있나」**다.
값의 성질만 적고, 그것으로 무엇을 할지는 `01`·`03`·`05`가 갖는다.

## 결론 먼저

| 물음 | 답 |
|---|---|
| 7항목을 4종 모두 채웠는가 | 09-22 표본 8건으로 값 형태를 확인했다. API 과거 커버리지와 누적 전수는 아직 확정하지 않았다. |
| 가장 큰 발견 | 제재공시 응답의 날짜 필터는 **`inputDate`(공시 입력일시) 기준이다, `actReqDate`(제재조치일)가 아니다.** 08-25 조치된 건이 09-03 입력되어 09월 조회에 걸려 나온 사례로 확인했다(7절) — 15의 「어느 칸에 필터가 걸리는지 모름」이 해소됐다 |
| 표 구조를 바꿀 문제 | **2건** (8절). 09-20 금투협 실측으로 한 건이 소멸했다. 둘 다 「무엇을 분모로 세는가」 문제다 |
| 09-14에 「모름」이던 판매사 표기 | **해소.** 소스 셋이 각각 다르게 준다(4절) |

## 0. 읽는 법 — 이 표의 4종은 「문서 단위」다

`00b` 3절이 정한 대로, 전수와 결측률을 같은 표에 놓을 수 있는 것은
**DART 펀드공시 · 제재공시 · 분쟁조정결정례 · 금투협 수시공시** 넷뿐이다.
행 하나가 「공시 문서 1건」이고 발행일·발행 주체·본문·첨부가 공통이다.

**finlife · KRX · 공공데이터포털은 이 표에 넣지 않는다.** 결측의 뜻이 다르기 때문이다.

| | 결측의 뜻 |
|---|---|
| 문서 4종 | 「문서에 첨부가 없다」 |
| API 3종 | 「필드 값이 비어 있다」 |

**기간 창은 통일하지 않는다 (09-14 결정).** 최근 90일로 자르면 분쟁조정이 사실상 0건이 되는데,
분쟁조정은 골든셋 라벨이라 누적 전체를 봐야 한다.

## 3. 값 표기 방식

| 소스 | 실측된 표기 |
|---|---|
| DART 펀드공시 | 위험등급이 **`2등급[높은 위험]` / `2등급[ 높은 위험 ]` / `2등급[높은 위험 ]`** — 표본 10건 안에서 **공백 변형 3종**. 1~6등급이며 **1등급이 최고위험** |
| 제재공시 | **09-22 실측 (표본 8건).** 응답 인코딩 `euc-kr`, `resultCode` 네 갈래(위와 동일, 15절). **레코드 안의 값**: `actReqDate`는 `2026.9.17.`처럼 **`YYYY.M.D.`(월·일 앞자리 0 생략, 끝에 점)**, `inputDate`는 `2026-09-17 13:30:31.0`처럼 **`YYYY-MM-DD HH:MM:SS.f`**로 서로 다른 두 표기 체계다. `finInstName`(금융회사명)의 법인격 표기 **위치가 회사마다 다르다** — `㈜비엔케이투자증권`(전치)과 `다올투자증권㈜`(후치)가 같은 표본 안에 섞여 있다(`05` 9절 3단계가 「위치 무관 제거」를 요구하는 이유가 이 실측으로 확인됨) |
| 분쟁조정결정례 | 해당 없음 (위험등급·수수료 같은 정형 값이 없는 서술형 문서) |
| 금투협 수시공시 | `standardCd` 접두가 **3종** — `K55` 887 / `KR5` 603 / `KRM` 9. **한 칸에 두 코드 체계가 섞인다**(`12`). PDF 본문의 위험등급은 `투자 위험등급 N등급[명칭]` |

**공백 변형은 정규식으로 흡수해야 한다.** `「(\d)등급`만 보고 뒤를 버리는 것이 안전하다.

## 7-1. 실물 보기 (09-20 추가)

위 표들은 성질만 적었다. **값이 실제로 어떻게 생겼는지**를 붙인다. 이것이 없으면
「판매사명이 마스킹」이나 「15행」 같은 말이 읽는 사람에게 와닿지 않는다.

### 금투협 수시공시 — 한 공고가 목록에서 15행

한국투자신탁운용 2026-08-13 공시 **1건**이다(`reference/kofia_ann_sample.csv`).

| # | `standardCd` | `uFundNm` |
|---|---|---|
| 1 | `KR5101644916` | 한국투자차이나베트남증권투자신탁 1(주식) |
| 2 | `K55101BP2277` | **`└▶`** 한국투자차이나베트남증권투자신탁 1(주식)(A-G) |
| 3~15 | `K55101…` / `KR5101…` | **`└▶`** …(C-G) (C-P) (C-R) (C-Re) (A) (C1~C5) (S) (A-e) (C-e) |

**1행이 모펀드, 2~15행이 클래스**다. 클래스 행은 펀드명이 **`└▶`로 시작**한다 — 화면의
들여쓰기가 응답에 그대로 들어 있고, 이것이 모·자를 가르는 유일한 신호다.
괄호 안은 판매 경로와 보수 체계만 다른 **같은 펀드**다.

**15행 전부 `announceTtl`·`standardDt`·`companyCd`가 같고 `standardCd` 하나만 다르다.**
그리고 `standardCd`에 `KR5`와 `K55` 두 체계가 섞여 있는 것도 이 표에서 그대로 보인다.

### ETF 이름 대조 — 세 갈래가 어떻게 생겼나

`reference/etf_rule_check.csv` 1,602행에서 구분별로 뽑았다.

| 구분 | KRX `ISU_NM` | 포털 `fndNm` |
|---|---|---|
| **일치** (938) | `1Q 200액티브` | `하나 1Q 200액티브증권상장지수투자신탁[주식]` |
| **매칭 실패** (229) | `ACE 200TR` | — (붙는 펀드명 없음) |
| **오탐 후보** (435) | — | `삼성 KODEX 미국AI메모리TOP2플러스증권상장지수투자신탁[주식]` |

**「매칭 실패」가 왜 안 붙는지가 여기서 보인다.** KRX는 `ACE 200TR`이라는 **상장 약명**을
주는데, ACE는 구 KINDEX라 포털의 정식 펀드명과 브랜드가 아예 다르다. 문자열로는 못 좁힌다.

### DART 위험등급 — 같은 값이 세 가지로 적힌다

표본 10건 **안에서** 나온 변형이다(`09`).

```
2등급[높은 위험]      2등급[ 높은 위험 ]      2등급[높은 위험 ]
```

**정규식은 `「(\d)등급`까지만 보고 뒤를 버려야 안전하다.**

### 분쟁조정 — 마스킹이 실제로 어떤 모양인가

```
【 ○○○ : ●●증권 】
▣▣ ▤▤▤▤▤ 아시아 무역금융 전문투자형 사모투자신탁1호
●●손해보험㈜    ●●카드㈜    ○○○○○○ 주식회사
```

**회사명은 `●`, 상품명은 `▣`·`▤`로 가려진다.** 업종(증권·은행·보험·카드)만 남는다.

### 제재공시 — 본문이 어떻게 가려지나

금감원 공개 샘플의 `actObjContent`다. **상품·사람·지점·거래처가 전부 기호다.**

```
잘못 매수한 ㉮펀드(가입액 10백만원)를 환매하고 … 乙 본인 자금으로 ㉮펀드를 매수하여
甲에게 … A지점은 2007.11.1. … ㈜C(대표 戊) 등 15개 업체에 대하여
```

반면 **금융회사명은 실명**이다 — 샘플 값이 `교통은행`이다. 법인격 표기가 없는 약칭이다.

**09-22 실측 (2026-09 조치 8건)**: 위 마스킹 패턴을 실제 데이터에서도 확인했다. 또한 이 8건 중
2건이 보험대리점 제재라, `㉮`가 펀드 전용이 아니라 **`㉮보험`으로도 쓰이는 범용 상품 마스킹
기호**임이 드러났다.

```
잘못 매수한 ㉮펀드를 환매하고 甲에게 … A지점은 2007.11.1. … B증권 등 위법한 거래*를 감추어 주기 위해,
* u2018제3자 이익도모 금지 회피 목적의 투자일임·신탁재산 간 연계거래u2019 등으로
```

**두 번째 줄이 인코딩 이상이다.** 작은따옴표 두 개가 문자가 아니라 **`u2018`·`u2019`라는 4글자
문자열 그대로** 들어 있다(표본 8건에서 35회). 줄바꿈 자리에도 **`n`이라는 글자 하나가 그대로**
섞인다(`"…항n(1) …"`, 표본 8건에서 **202회**) — 이스케이프 처리 중 문자가 아니라 이스케이프
코드 이름이 본문에 남은 것으로 보인다. 본문을 사람이 읽거나 마스킹 검증에 쓰려면 이 패턴들을
먼저 치환해야 한다.

**표본 8건의 실측 횟수** — 본문 4칸(`actObjContent`·`actOrganCon`·`actOfficerCon`·`actEmpCon`) 기준.

| 들어 있는 글자 | 원래 문자 | 횟수 |
|---|---|---|
| `u2018` + `u2019` | 작은따옴표 | 35 |
| `u2027` | 가운뎃점 | 3 |
| `u2020` | † (각주) | 4 |
| `u203B` | ※ | 1 |
| `n` | 줄바꿈 | **202** |

**`n` 202회의 세는 규칙**: 위 네 칸에서 소문자 `n`을 전부 센 값이다. 이 표본에는 알파벳 `n`이 들어간
영어 단어가 하나도 없다 — 익명화 표기가 `A팀`·`E팀`·`F스쿼드`처럼 한 글자여서 `n`이 단어의 일부로
나오는 경우가 없다. 그래서 202개 전부가 줄바꿈 자리다.

**09-22 정정**: 처음에 「약 85회」로 적었고 주영 티켓에는 「59회」로 넘겼는데 **둘 다 틀렸다.**
한글 사이에 낀 `n`만 세는 좁은 규칙을 썼기 때문이다(그 규칙으로는 21~136회가 나온다).
눈대중이 아니라 위 규칙으로 다시 세어 202로 고쳤다.

### 운용사 구 상호 — 유사도로 못 잡는 이유

`reference/kofia_mgmt_codes.csv` 536건 중 **97건(18%)**이 구 상호를 갖는다.

```
누림투자자문  →  누림자산운용        (업종 접미사까지 바뀜)
아주자산운용(주) / 파란자산운용 / 아이스텀자산운용 / 도이치자산운용
```

**「투자자문」과 「자산운용」은 문자열 유사도로 이어지지 않는다.** 치환 사전이 필요하고,

## 8. 표 구조를 바꿀 문제 — 2건

티켓 완료 조건 2번이 요구한 「3건 이하」다. 둘 다 **「무엇을 분모로 세는가」** 문제다.

**초판은 3건이었다.** 「「전수」 칸이 모든 소스에 성립하지 않는다」를 문제 1로 들었는데, 그 근거였던
「금투협은 조회 창이 1년이라 누적 전수가 없다」가 09-20 실측으로 성립하지 않게 되어 **사라졌다**(1절).

### 문제 1. 분쟁조정은 분모가 셋이다

**사건 814건 / 금융투자 187건 / 첨부 845개**가 모두 다른 분모다.
「추출 성공 112건」은 **첨부 213단위** 기준이고 사건 187건이 아니다.
결측률을 적는 칸에 **분모를 함께 적는 칸**이 없으면 이 숫자들은 반드시 섞인다.

### 문제 2. 「결측」이 두 가지 뜻으로 쓰인다

문서 4종에서는 「첨부가 없다」, API 3종에서는 「필드가 비었다」다.
`01`의 원본파일 표와 상품 표가 각각 다른 뜻의 결측을 담는데 **칸 이름이 같다.**
`03`의 실패 상태값처럼 **원인을 구분하는 값**이 결측에도 필요하다.

## 8-1. API 과거 조회의 0건 응답과 미확정 커버리지

**기존 조회 기록**에는 2026-01~08을 조회해 정상 0건(`900`)을 받았다고 적혀 있다. 다만 28일×9구간이라는 요약만으로 실제 요청 시작·종료일과 누락 없는 범위를 입증할 수 없어, 전체 커버리지는 요청 로그 대조 후 확정한다.

| 조회 구간 | 결과 |
|---|---|
| 2026-01~08 조회 기록 | **0건 보고. 정확한 요청 구간·누락 여부 재검증 필요** |
| 2026-09-01 ~ 2026-09-30 | **8건** |
| 최근 24개월 월별 (09-21 실측) | 2026-09만 자료 있음, 나머지 전부 `900` |

**게시판 경로는 2000년 이후 5,735건이다.** 저장된 API 표본은 8건이며, 게시판과의 범위·키 대응은 미확정이다.

09-21 기록은 최근 24개월 월별 조회를 보고한다. 이것은 해당 호출에서의 관찰이며, API의 영구 보존 정책이나 더 오래된 자료의 부재를 입증하지 않는다.

**왜 이런지는 확인하지 못했다.** API가 최근 입력분만 노출하는 구조로 보이지만, 금감원 문서에 그런 설명이 없고 호출로 더 확인하려면 조회 한도를 더 써야 한다. **추정이지 사실이 아니다.**

**이것이 막는 일**: 민석 「판매사별 라벨 표 — 제재공시 기반」(10-07)은 판매사마다 제재 이력을 세는 작업이다. API만 쓰면 재료가 8건뿐이라 표가 성립하지 않는다. **게시판 경로(5,735건)를 쓰거나, API의 노출 범위를 금감원에 확인하거나 둘 중 하나가 필요하다.** 10-07 전에 정해야 한다.


## 9. 「모름」과 그 이유

티켓 규칙이 「모르면 모름이라 적고 이유를 1줄 단다」이므로 그대로 따른다.

| 항목 | 이유 |
|---|---|
| 제재공시의 2·3·6항목 (결측·값 표기·이상값) | **09-22 해소.** 일일 한도가 자정을 지나 복구된 뒤 `--from 2026-09-01 --to 2026-09-30` 1회 조회로 8건 전량을 받아 2·3·6절에 반영했다 |
| 금투협 누적 전수 | **미측정.** 측정 가능하다(1절). 1년 미만 창으로 쪼개 세면 된다 |
| 제재공시 2026 연초 누적 | **미확정.** 저장 표본은 8건이며 요청 구간·완전성·게시판 대조가 필요하다. |
| 제재공시 증분 필터 대상 필드 | **09-22 해소.** `inputDate`로 확정했다(7절) |
| 금투협 2026 연초 누적 | 조회 창 1년 안에 들어오므로 받을 수는 있으나, **아직 받지 않았다** |
| DART 연초 누적 6,473건의 기준 기간 | `00b`가 추정으로 표시. 확정 안 됨 |

**「측정 불가」로 분류할 항목은 없다.** 남은 항목(금투협 누적 전수·제재공시 연초 누적·금투협 연초 누적·DART 기준기간)은 전부
「미측정」이고, 방법은 정해져 있다 — 호출을 몇 번 더 하면 닫힌다.

팀의 09-05 기록을 옮긴 것이고 이 저장소의 실측이 아니다. 경로가 생겼으므로 재측정이 가능하다.
