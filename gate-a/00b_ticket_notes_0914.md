# Notion 티켓 본문 메모 사본 (09-14, 대현 작성) — 에이전트 공유 입력

두 티켓의 토글에 적힌 검토 메모를 그대로 옮겼다. 우리 초안(01~08)과 대조해 반영할 것을 찾는 데 쓴다. 이 메모는 「팀 실측 기록 + 09-14 교차 검증 4건(숫자 검산, 통계 설계, 논리 스키마, 외부 사실 확인)」에 근거한다고 되어 있다.

## A. Schema 티켓 「09-16 확정 전 반영 항목 (검증 결과, 09-14)」

### A1. 가장 먼저 정할 것 — 문서 표의 한 줄
- 권고: **「수집한 원천 문서 1건」**. DART는 접수번호 단위, 금투협은 공고 1건 단위이며 클래스 단위가 아님.
- 근거 셋: (1) 금투협 15행이 가리키는 실제 PDF는 하나. 클래스 단위로 두면 같은 PDF에 15개 행이 붙어 본문 추출을 15번 수행. (2) 문서 한 줄이 원본 파일 하나와 1:1로 대응해야 원본 경로·콘텐츠 해시·추출 상태·재처리 단위가 같은 입자에서 관리됨. (3) DART는 같은 사건을 펀드 단위 1건으로 제공하므로 두 소스의 입자를 통일하려면 더 굵은 쪽으로.
- 상품과의 연결은 **별도 브릿지 표로 분리**. 문서 대 상품의 카디널리티는 1:N.

### A3. 이름 매칭 규칙
- **`증권투자신탁`과 `증권자투자신탁`의 「자」 한 글자는 모·자를 가르는 결정적 정보.** 유사도 점수로는 드러나지 않으므로 호수·클래스 표기와 함께 별도 필드로 뽑아 **다르면 점수와 무관하게 탈락**.
- 정규화 순서: NFKC → 공백 전면 제거 → `(주)` 제거 → 유형 괄호·호수·클래스 표기를 별도 필드로 분리.
- 임계치는 용도별 두 벌: DART 1단계는 자동 확정 없이 0.80 미만만 후보에서 제외(재현율 우선). 코드가 영원히 없는 분쟁·제재는 0.95 이상이면서 단독 후보이고 판매사명도 일치할 때만 확정.
- 분쟁·제재 187건은 자동 확정하지 말고 **전건 수동 확인** 권고.

### A4. 원본 보관 규칙
- 경로: `raw/{source}/{yyyy}/{mm}/{dd}/{source_doc_key}/{filename}`
- **덮어쓰지 않고 쌓음.** 정정본과 게시판 첨부 교체 때문에 덮어쓰면 과거 시점을 재현할 수 없음.
- 파일 실체는 `blobs/{sha256 앞 2자}/{sha256}`에 두고 사람이 읽는 경로는 `raw_object.storage_path`에만 남김. 심볼릭 링크는 만들지 않음.

### A5. 실패 처리 규칙 3건의 상태값
- 수집 안 됨: 타임아웃과 5xx만 지수 백오프 5회 재시도. 403은 설정 오류이므로 재시도 없이 즉시 알림.
- 본문 뽑기 실패: HWP 3.0 94건은 `EXTRACT_UNSUPPORTED_FORMAT`, 배포용 7건은 `EXTRACT_PARTIAL`(BMP 4건은 `OCR_CANDIDATE` 보조 플래그). **둘 다 자동 재시도에서 제외.** DART `document.xml`의 본문 부재는 실패가 아니라 `EXTRACT_NOT_APPLICABLE`.
- 상품 못 찾음: `PENDING_MASTER`(정상 대기, 30일 재시도) / `AMBIGUOUS`(수동 큐) / `NO_CANDIDATE`(주 1회) / `NO_CODE_IN_SOURCE`(분쟁·제재의 구조적 특성).

### A7. 09-15 실측으로 확인할 가정 2건 (각 40분)
- **금투협 15행이 가리키는 PDF가 동일 파일인가.** 같은 `announceTtl`·`standardDt`를 공유하고 `standardCd`만 다른 행 묶음의 PDF `sha256sum` 비교. 같으면 문서 입자를 「공고 1건」으로 확정. (외부 확인에서 「15가 클래스 개수가 아니라 기본 조회 건수일 수 있다」는 지적이 독립적으로 나왔음.)
- **ETF 「상장지수」 문자열 규칙의 오분류율.** KRX ETF 1,167건(2026-09-04)과 공공데이터포털 `fndNm` 「상장지수」 포함 집합을 대조해 일치·누락·오탐·잔여 네 수. 누락·오탐 각 1% 미만이면 규칙 유지, 오탐이 유의미하면 KRX 대조를 1차 판정으로 승격.

## B. 「데이터 가져온거 보고 분석해보기」 티켓 「대현, 09-14」 메모 (스키마에 관련된 부분만)

### B1. 소스 정의
- 전수와 결측률을 같은 표에 놓을 수 있는 것은 **공시 문서 단위 4종**: DART 펀드공시, 제재공시, 분쟁조정결정례, **금투협 수시공시**. 행 하나가 「공시 문서 1건」이며 발행일·발행 주체·본문·첨부 공통.
- 실제 사용 중인 데이터는 **8종**: 인증키 필요 5종(finlife, OPEN DART, KRX, 국가법령정보, 공공데이터포털 펀드상품기본정보), 불필요 3종(금투협 전자공시, 분쟁조정결정례, 제재공시).
- 문서 4종의 결측 = 「첨부가 없다」, API 3종의 결측 = 「필드 값이 비어 있다」. 같은 열에 넣지 않음.
- 분쟁조정: 사건 814건, 첨부 파일 845개(분모가 다름). 첨부 213단위 중 HWP 3.0 94건, 배포용 7건(BMP 내장 4건은 PrvText로 약 1,022자 부분 복구).
- 기간 창은 통일하지 않음(09-14 결정). 분쟁조정은 골든셋 라벨이므로 누적 전체.
- DART 투자설명서 전수: 90일 창 2,337건(6,473은 연초 누적 추정). 제재공시 5,735건(2000년 이후 누적).

### B2. 재조사 불필요 항목의 답
- 값 표기: 금투협 PDF 「투자 위험등급 N등급[명칭]」, DART 「투자위험등급 2등급[ 높은 위험 ]」. 띄어쓰기 변형. 1~6, 1이 최고위험.
- 상품명 표기: DART 「미래에셋밸런스롱숏증권자투자신탁1호(채권혼합)」 vs 금투협 「미래에셋밸런스롱숏증권자투자신탁 1(채권혼합)」. **펀드명은 조인 키로 부적합 확정.**
- 기간 분포: 공공데이터포털 `basDt`는 코드 등록·갱신 기준일. 증분은 `beginBasDt`로 받은 뒤 `setpDt`로 필터.
- 위험등급 원문이 있는 소스는 펀드 투자설명서뿐. finlife·KRX는 필드 부재.
- 수수료: 어느 API에도 없음. 투자설명서 본문 추출값.
- 판매사 이름 표기: 출처 **미정**. 공공데이터포털에는 운용사 필드조차 없음.

### B3. 분석 시 주의
- 112(추출 성공), 94(HWP 3.0), 7(배포용)은 전부 **파일 단위**. 사건 187건 아님.
- finlife 식별 필드: 「38건 전부 유일」은 상품 단위, 「152건 조인 성공」은 옵션 단위(152 ÷ 38 = 4.0). 914건 전수 재확인 필요. → (우리 쪽 주의: finlife에 일반 공모펀드는 없지만 **연금저축상품 API에 연금저축펀드가 포함**될 수 있음. 914건의 정체 확인 필요.)

### B4. 09-16 스키마 확정으로 이관한 항목
- 문서 표의 한 줄 확정: 「수집한 원천 문서 1건」. DART 접수번호 단위, 금투협 공고 1건 단위.
- 위험등급은 상품 표의 칸이 아니라 **문서에서 추출해 채우는 값**.
- 금투협 클래스 중복 제거 규칙 필요(문서 1건이 15행).
- 조인 키 단일 의존 위험 → 실패 목록을 판매사별·상품유형별로.

### B5. 09-15 액션 (담당 미정 2건)
- 금투협 15행 동일 PDF 여부(sha256), ETF 「상장지수」 오분류율. 제재공시 OPEN API 인증키 신청은 주영(09-15).
